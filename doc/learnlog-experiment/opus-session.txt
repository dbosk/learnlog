     Plan: Variation-theory annotations for learnlog.tex

     Context

     learnlog.tex is a transcript of a student (Daniel Bosk) debugging
     contacts.py over five Edit/Run cycles. The transcript shows the what —
     code, diffs, errors, output — but not the why of what the student did and
     did not learn.

     The user wants to annotate the transcript using variation theory (Marton):
     under each two-column pair (Run|Edit or Edit|Run), describe what the pair
     makes visible and what the underlying variation pattern lets the student
     discern (and what it does not). This turns the transcript into a teaching
     artefact about how debug-driven testing exposes — and hides — information.

     Approach

     The document layout puts each Edit and Run inside \begin{minipage} columns
     arranged in eight rows separated by \vspace{1em}. Insert one short visible
     analysis paragraph inside the \vspace{1em} separator after each row,
     spanning the full text width (i.e. outside the two minipages, after the
     right-hand \end{minipage} but before the next row's \vspace).

     Each annotation block:

     - begins with \paragraph*{Variation-theory note} (starred, no TOC entry);
     - is short (4–6 lines), so the visible flow of the transcript dominates;
     - uses the skill's vocabulary explicitly: critical aspect, what varies,
     what stays invariant, discerned, not yet discernible.

     Language: English, matching the document's framing text. Code-level Swedish
     comments stay untouched. No new packages required (only \paragraph* and
     standard LaTeX, already in use).

     Note on the layout: the document deliberately repeats each Edit/Run across
     two adjacent rows (each item appears once on the right paired with what
     follows, then again on the left paired with what came before). The
     annotations therefore also revisit the same items from different angles —
     the row's juxtaposition is the unit of analysis, not the items themselves.

     Per-row annotations (drafts)

     Row indexing uses the LaTeX line numbers of the closing \end{minipage}
     of the right-hand column.

     Row 1 — Run 1 | Edit 2 (after line 293)

     - Critical aspect: the boolean operator joining value is not None and
     not value.isdigit() in the phone setter.
     - What varies between the two columns: only the operator (or → and).
     Everything else — sub-conditions, message, surrounding control flow — is
     invariant. This isolates the operator as the cause.
     - What is discerned: the traceback chain __init__ → setter → raise
     makes the property mechanism visible. The single test value
     phone="0701233455" (digit string, non-None) is enough to falsify or
     (its left operand is true, so the disjunction is true regardless of the
     right operand) but not enough to verify and.
     - Not yet discernible: behaviour for value=None (the TODO's stated
     goal) and for non-digit strings. Three values
     {None, "0701…", "abc"} would separate the roles of the two sub-conditions;
     only one value is tried.

     Row 2 — Edit 2 | Run 2 (after line 355)

     - Critical aspect: control flow downstream of the constructor.
     - Reading the juxtaposition: with the setter unblocked, execution now
     proceeds far enough to reveal a different defect — a while True in
     find_contact with no break condition, surfaced as KeyboardInterrupt.
     - What is discerned (by contrast with Run 1): Edit 2's fix held;
     the constructor no longer raises. The new failure point lies elsewhere.
     - Not yet discernible: whether the search results themselves are
     correct. The transcript shows stdout but not stdin, so the queries that
     produced the listed matches are invisible.

     Row 3 — Run 2 | Edit 3 (after line 421)

     - Critical aspect: how to leave an interactive while True.
     - What varies: the input handling — from a single .strip() chain to a
     branch on emptiness (if not search_terms: break).
     - What is discerned: empty input is now a recognised exit signal; the
     inner loop becomes escapable without Ctrl-C.
     - Not yet discernible: whether __lt__ orders ties correctly (only two
     contacts exist), whether multi-term queries accumulate match counts as
     intended, and whether match_contact's exact-equality branch for phone
     numbers behaves differently from the substring branches — none of these
     dimensions varies in the transcript.

     Row 4 — Edit 3 | Run 3 (after line 470)

     - Critical aspect: that Edit 3 closes the loop without affecting the
     successful path.
     - Reading the juxtaposition: the contrast Run 2 → Run 3 (with Edit 3 in
     between) is exactly the contrast variation theory recommends — same
     invocation, only the loop-exit logic differs.
     - What is discerned: the menu now reaches Exit code: 0; option 5 ends
     the program cleanly.
     - Not yet discernible: the search returned only Daniel, but the query
     is unrecorded. A "1 expected match" reading is indistinguishable from a
     "should have been 2, returned 1" reading.

     Row 5 — Run 3 | (empty) (after line 502)

     - This row is Run 3 alone (the right minipage is empty). It carries no new
     variation — it is a layout repeat of the same successful execution.
     - Note: a row with no contrasting partner offers no new dimension to
     discern; if every cycle were like this, no learning would occur.

     Row 6 — (empty) | Run 4 (after line 534)

     - Run 4 is identical in inputs and outputs to Run 3.
     - Variation-theory reading: repeating a successful run with the same
     inputs adds no new variation, hence no new discernment. To learn more
     about the search/sort, the student would need to vary either the query
     (different terms, multi-term, exact phone), the contact set (more rows,
     ties on different attributes), or both.

     Row 7 — Run 4 | Edit 5 (after line 582)

     - Critical aspect: whether Edit 5 changes any behaviour.
     - What varies: only whitespace inside the NotImplementedError call —
     no semantic dimension changes.
     - Reading the juxtaposition: a non-variation. If Run 5 differs from
     Run 4, the cause is something else (input choice), not Edit 5. This is a
     useful invariance check — formatting edits should leave behaviour
     unchanged.

     Row 8 — Edit 5 | Run 5 (after line 633)

     - Critical aspect: the else arm of the menu dispatcher.
     - What varies (vs. earlier runs): the menu choice — an unrecognised
     option this time. Edit 5 is held invariant on semantics, so the new
     failure must come from the input dimension.
     - What is discerned: the catch-all branch correctly raises
     NotImplementedError.
     - Not yet discernible: options 3 and 4 (pass placeholders) silently
     return to the menu — distinct from option 5 (clean return) and from the
     catch-all (raise). None of the runs separates these three outcomes.
     Likewise, non-numeric input (which would raise ValueError from
     int(...)) is never tried.
